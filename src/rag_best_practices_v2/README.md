이 문서는 삼성전자 사업보고서 RAG 시스템의 성능을 한 단계 더 끌어올리기 위해 도입한 **Markdown 기반 테이블 플레이스홀더(Placeholder) 기법**의 실험 결과와 최적화 전략을 정리한 기술 보고서입니다.

## 🏆 Executive Summary (최종 권장 아키텍처)

테이블 데이터 복원 기법을 적용한 후의 최적 RAG 파이프라인 구성은 다음과 같습니다.

| Component | Recommendation | Reason |
|-----------|----------------|--------|
| **Embedding** | `intfloat/multilingual-e5-large` | 한국어 텍스트 및 마크다운 테이블 구조 이해도 우수 |
| **Table Processing** | **Placeholder + Markdown Restoration** | 테이블 파편화 방지 및 구조적 의미 보존 (Precision 상승) |
| **Chunking** | **512 Tokens (w/ Table Weight)** | 테이블 마크다운을 훼손하지 않고 텍스트 문맥과 함께 담을 수 있는 최적의 밸런스 구간 |

| 방식 (Chunk 512 기준) | CR (Relevance) | Precision | Recall | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| **Baseline (기존 방식)** | 0.898 | 0.731 | 0.727 | 표 데이터가 끊겨서 일부만 검색됨 (정보 손실) |
| **v4 (테이블 마크다운 복원)** | **0.926** | **0.816** | **0.783** | **정확도(Precision) 약 11.6%p 대폭 상승** |

## 1. 실험 배경 및 목표
- **도메인 특성**: 재무제표, 이사회 현황, 임원진 정보 등 사업보고서에는 검색의 핵심이 되는 방대한 **표(Table)** 데이터가 다수 존재합니다.
- **평가 데이터셋**: 본 실험에서는 텍스트와 표 정보가 복합적으로 등장하는 문서 특성을 반영하기 위해 고품질의 병합 평가셋인 [**`eval_dataset_v3_merged.csv` (클릭하여 이동)**](../../data/eval_dataset_v3_merged.csv)를 활용하여 Ragas (Context Relevance, Precision, Recall) 성능을 채점했습니다.
- **기존의 한계(Baseline)**: 일반적인 Text Splitter를 사용해 일괄적으로 자르면 표 내부의 행과 열 구조(Context)가 찢어집니다. 따라서 특정 수치 검색 시 행/열 헤더 정보가 유실되어 오답률이 급증하는 문제점이 발생했습니다.
- **해결 방안(v4)**: 전처리 단계에서 표를 `[TABLE_0_1]` 형태의 **임시 플레이스홀더(Placeholder)** 텍스트로 치환해 두고 문장 청킹을 진행합니다. 청킹이 완료된 후 각 Chunk 내부에 포함된 플레이스홀더들을 **진짜 Markdown 형식의 테이블 데이터로 복원(Restore)**하여 최종 Vector DB에 삽입합니다.

## 2. 실험: Chunking Strategy with Table Restoration

### 실험 내용
동일한 평가 데이터셋 하에서, **테이블 파편화 처리(Baseline)** 문서와 **테이블 마크다운 복원(v4)** 문서 각각에 대해 청크 사이즈(256, 512, 1024)별 검색 품질을 Ragas 지표(Context Relevance, Precision, Recall)로 측정했습니다.

### 주요 결과 (Baseline - 테이블 분할 오류 방치)
| Chunk Size | CR (Relevance) | Precision | Recall |
|------------|----------------|-----------|--------|
| **256**    | 0.897 | 0.771 | 0.722 |
| **512**    | 0.898 | 0.731 | 0.727 |
| **1024**   | 0.874 | 0.730 | 0.737 |

### 주요 결과 (v4 - 테이블 마크다운 복원 처리 완료)
| Chunk Size | CR (Relevance) | Precision | Recall | 평가 📝 |
|------------|----------------|-----------|--------|------|
| **256**    | 0.905 | 0.793 | 0.728 | 표가 물리적으로 큰 경우 청크 영역을 초과할 소지가 높음 |
| **512**    | **0.926** | **0.816** | **0.783** | **최적 성능**. 테이블의 마크다운 구조와 주변 설명글을 온전히 담기에 가장 이상적임 |
| **1024**   | 0.931 | 0.790 | 0.809 | Recall은 소폭 오르나 엉뚱한 정보 혼입으로 Precision 저하 |

> **💡 Insight**: 
> 1. 테이블의 구조를 마크다운으로 깔끔히 유지해서 삽입하는 것만으로 **거의 모든 청크 사이즈 및 지표에서 성능이 급상승**합니다. 특히 512 토큰 기준 **Precision이 무려 11.6% 포인트(0.731 -> 0.816)** 상승하며 압도적인 정확도를 증명했습니다.
> 2. 기존 일반 텍스트 중심 RAG 최적화(v1)에서는 256 토큰이 최고였지만, **마크다운 표 구조를 온전히 보존해야 하는 테이블 RAG 환경에서는 512 토큰 부근**이 행/열 데이터를 잘리게 하지 않을 가장 안전하고 뛰어난 성능을 보입니다.

## 3. 핵심 아키텍처 요소: Table Weight & Custom Length Function

마크다운 표본이 통째로 복원될 시 LLM 프롬프트가 지원하는 '최대 토큰 길이를 초과'하는 에러를 막기 위해 **커스텀 가중치 로직**을 새롭게 고안하여 적용했습니다 (`chunking.py`).

1. **가중치 부여**: 마크다운 형식의 테이블은 `|`나 `-` 기호 등으로 인해 일반 텍스트보다 토큰 소비량이 많습니다. 따라서 복원 시 할당할 길이에 **테이블 가중치(예: 1.6x)**를 곱셈 처리합니다.
2. **선행 청킹 (Early Cut)**: 청크 분할기가 문서를 자르기 직전에, 문자 내부의 `[TABLE_x_y]` 영역을 감지하고 가중치가 더해진 어마어마한 테이블 넓이를 미리 예측하여 텍스트를 예상보다 '일찍(안전하게)' 잘라버립니다.
3. 이 기술 도입으로 LLM Context 윈도우 한계를 넘어서는 에러를 원천적으로 차단했으며, 구조적인 안정성에 크게 기여했습니다.

## 4. 결론 및 실무 제언 (Next Step)

1. **테이블 데이터의 1원칙 "분리, 보존, 그리고 병합"**: 금융업 또는 공공기관 기술 보고서처럼 정형 데이터(표)와 비정형 데이터(텍스트)가 거미줄처럼 엮어있는 문서는 일반 추출기가 한 번에 삼키게 둬선 안 됩니다. 
   PDF 파싱 단계에서 미리 표를 모두 독립 추출(Extraction) 한 뒤 마크다운의 형태로 텍스트 사이에 다시 끼워주는 것이 검색 품질 향상의 황금열쇠입니다.
2. **청크 사이즈의 재조정**: 앞으로 마크다운 테이블이 포함되는 데이터베이스에서는 청크 사이즈를 최소 **512 이상** 넓게 가져가십시오.
