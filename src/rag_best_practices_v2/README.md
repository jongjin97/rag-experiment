# Samsung Business Report RAG Optimization v2 (테이블 처리 고도화)

이 문서는 삼성전자 사업보고서 RAG 시스템의 성능을 한 단계 더 끌어올리기 위해 도입한 **Markdown 기반 테이블 플레이스홀더(Placeholder) 기법**의 실험 결과와 최적화 전략을 정리한 기술 보고서입니다.

## 🏆 Executive Summary (최종 권장 아키텍처)

테이블 데이터 복원 기법을 적용한 후의 최적 RAG 파이프라인 구성은 다음과 같습니다.

| Component | Recommendation | Reason |
|-----------|----------------|--------|
| **Embedding** | `intfloat/multilingual-e5-large` | 한국어 텍스트 및 마크다운 테이블 구조 이해도 우수 |
| **Table Processing** | **Placeholder + Markdown Restoration** | 테이블 파편화 방지 및 구조적 의미 보존 (Precision 상승) |
| **Chunking** | **512 Tokens (w/ Table Weight)** | 테이블 마크다운을 훼손하지 않고 텍스트 문맥과 함께 담을 수 있는 최적의 밸런스 구간 |
| **Retrieval** | **Hybrid (Dense + BM25) + HyDE** | 키워드/의미론적 검색 결합(Hybrid)에 가상 답변(HyDE) 확장을 더해 지표 전반(Relevance, Precision, Recall) 상승 확인 |

### 📈 테이블 처리 유무에 따른 성능 비교 요약 (v4 Baseline vs v4)

테이블 데이터를 일반 텍스트처럼 잘라서 처리했을 때(Baseline)와 **구조를 보존하여 마크다운 표 전체로 환원**했을 때(v4)의 시스템 전체 평균 성능(Ragas 평가 지표) 차이는 다음과 같습니다.

| 방식 (Chunk 512 기준) | CR (Relevance) | Precision | Recall | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| **Baseline (기존 방식)** | 0.898 | 0.731 | 0.727 | 표 데이터가 끊겨서 일부만 검색됨 (정보 손실) |
| **v4 (테이블 마크다운 복원)** | **0.926** | **0.816** | **0.783** | **정확도(Precision) 약 11.6%p 대폭 상승** |

## 1. 실험 배경 및 목표
- **도메인 특성**: 재무제표, 이사회 현황, 임원진 정보 등 사업보고서에는 검색의 핵심이 되는 방대한 **표(Table)** 데이터가 다수 존재합니다.
- **평가 데이터셋**: 본 실험에서는 텍스트와 표 정보가 복합적으로 등장하는 문서 특성을 반영하기 위해 고품질의 병합 평가셋인 [**`eval_dataset_v3_merged.csv` (클릭하여 이동)**](../../data/eval_dataset_v3_merged.csv)를 활용하여 Ragas (Context Relevance, Precision, Recall) 성능을 채점했습니다.
- **기존의 한계(Baseline)**: 일반적인 Text Splitter를 사용해 일괄적으로 자르면 표 내부의 행과 열 구조(Context)가 찢어집니다. 따라서 특정 수치 검색 시 행/열 헤더 정보가 유실되어 오답률이 급증하는 문제점이 발생했습니다.
- **해결 방안(v4)**: 전처리 단계에서 표를 `[TABLE_0_1]` 형태의 **임시 플레이스홀더(Placeholder)** 텍스트로 치환해 두고 문장 청킹을 진행합니다. 청킹이 완료된 후 각 Chunk 내부에 포함된 플레이스홀더들을 **진짜 Markdown 형식의 테이블 데이터로 복원(Restore)**하여 최종 Vector DB에 삽입합니다.

## 2. 실험: Chunking Strategy with Table Restoration

### 실험 내용
동일한 평가 데이터셋 하에서, **테이블 파편화 처리(Baseline)** 문서와 **테이블 마크다운 복원(v4)** 문서 각각에 대해 청크 사이즈(256, 512, 1024)별 검색 품질을 Ragas 지표(Context Relevance, Precision, Recall)로 측정했습니다.

### 주요 결과 (Baseline - 테이블 분할 오류 방치)
| Chunk Size | CR (Relevance) | Precision | Recall |
|------------|----------------|-----------|--------|
| **256**    | 0.897 | 0.771 | 0.722 |
| **512**    | 0.898 | 0.731 | 0.727 |
| **1024**   | 0.874 | 0.730 | 0.737 |

### 주요 결과 (v4 - 테이블 마크다운 복원 처리 완료)
| Chunk Size | CR (Relevance) | Precision | Recall | 평가 📝 |
|------------|----------------|-----------|--------|------|
| **256**    | 0.905 | 0.793 | 0.728 | 표가 물리적으로 큰 경우 청크 영역을 초과할 소지가 높음 |
| **512**    | 0.926 | **0.816** | 0.783 | **최적 성능**. 테이블의 마크다운 구조와 주변 설명글을 온전히 담기에 가장 이상적임 |
| **1024**   | **0.931** | 0.790 | **0.809** | Recall은 소폭 오르나 엉뚱한 정보 혼입으로 Precision 저하 |

> **💡 Insight**: 
> 1. 테이블의 구조를 마크다운으로 깔끔히 유지해서 삽입하는 것만으로 **거의 모든 청크 사이즈 및 지표에서 성능이 급상승**합니다. 특히 512 토큰 기준 **Precision이 무려 11.6% 포인트(0.731 -> 0.816)** 상승하며 압도적인 정확도를 증명했습니다.
> 2. 기존 일반 텍스트 중심 RAG 최적화(v1)에서는 256 토큰이 최고였지만, **마크다운 표 구조를 온전히 보존해야 하는 테이블 RAG 환경에서는 512 토큰 부근**이 행/열 데이터를 잘리게 하지 않을 가장 안전하고 뛰어난 성능을 보입니다.

## 3. 실험: Retrieval Strategy (검색 방식 최적화)

### 실험 내용
최적의 Chunking 전략(테이블 마크다운 복원)이 반영된 데이터베이스를 바탕으로, 검색 품질 자체를 높이기 위해 세 가지 검색(Retrieval) 전략의 성능을 비교 분석했습니다. `eval_dataset_v3_merged.csv`를 기준으로 평가를 수행했습니다.

1. **Dense Retriever**: Vector DB(Chroma)에 저장된 임베딩 시맨틱 기반의 검색
2. **BM25 Retriever**: 전통적인 키워드/형태소 빈도수 기반의 어휘적 검색 알고리즘
3. **Hybrid (Ensemble) Retriever**: Dense와 BM25를 5:5 비율(`alpha=0.5`)로 결합한 검색 방식

### 주요 결과 (Retrieval 전략별 v4 세트 성능)
| Strategy | CR (Relevance) | Precision | Recall | 평가 📝 |
|:---|:---|:---|:---|:---|
| **Dense** | 0.929 | **0.808** | 0.779 | 높은 정밀도. 의미적 유사성을 통해 정확하고 연관성 높은 문맥 도출 |
| **BM25** | 0.780 | 0.662 | 0.653 | 단독 사용 시 가장 취약함. 어휘의 동의어 처리 및 거시적인 문맥 파악 미흡 |
| **Hybrid** | **0.931** | 0.723 | **0.858** | **가장 강력한 재현율(Recall)**. 전문 용어나 핵심 숫자를 절대 놓치지 않고 폭넓게 검색함 |

> **💡 Insight**: 
> 1. **재현율(Recall) 향상을 위한 Hybrid 전략의 우수성**: Hybrid 검색은 정답 문서를 놓치지 않고 찾아낼 확률(Recall 0.858)이 가장 높고, Context Relevance 역시 0.931로 매우 뛰어납니다. 반기보고서 내 특정 수치나 표 내 부속 정보를 찾을 때, 키워드망(BM25)과 시맨틱(Dense)이 보완 작용을 일으켜 큰 시너지를 냈습니다.
> 2. **Precision vs Recall 트레이드오프 현상**: 다만 Hybrid 사용 시 BM25가 가져온 일부 중복/노이즈로 인해 정밀도(Precision)는 Dense 단독(0.808) 대비 소폭 하락(0.723)하는 한계를 보였습니다. 이를 보완하기 위해 쿼리 확장(HyDE) 혹은 Re-ranker 모델의 도입이 권장됩니다.

## 4. 실험: HyDE (Hypothetical Document Embeddings) 적용 효과

### 실험 내용
가장 높은 재현율(Recall)을 보여준 **Hybrid (Dense + BM25)** 방식을 베이스라인으로 설정하고, 여기에 **HyDE** 전략을 추가하여 검색 성능의 완전한 개선 여부를 측정했습니다.
- **HyDE 동작 원리**: 사용자의 질문에 대해 빠른 추론 모델(`gpt-4o-mini`)이 먼저 "가상의 이상적인 답변"을 생성하고, 원본 질문과 가상 답변 텍스트를 하나로 합쳐서 VectorDB/BM25 검색을 수행하는 방식.

### 주요 결과 (Hybrid vs HyDE + Hybrid)
| Strategy | CR (Relevance) | Precision | Recall | 평가 📝 |
|:---|:---|:---|:---|:---|
| **Hybrid (Baseline)** | 0.931 | 0.728 | 0.853 | 준수한 성능을 보여주는 기존 베이스라인 |
| **HyDE + Hybrid** | **0.940** | **0.736** | **0.877** | **모든 지표(Relevance, Precision, Recall) 동반 상승** |

> **💡 Insight**: 
> 1. **검색의 한계(Recall) 돌파**: 가상의 답변을 통해 검색어(Query)를 확장하는 HyDE 전략은, 묻는 '키워드'를 넘어서 정답 문서가 가질 법한 '문맥과 전문 용어'까지 매칭 단위로 끌어올립니다. 결과적으로 정답 문서를 다 잡아내는 **Recall 지표가 0.853에서 0.877로 추가 상승**했습니다.
> 2. **Hybrid의 약점(Precision) 극복**: 기존 Hybrid 방식의 약점이었던 불필요한 노이즈 혼입(Precision 저하) 현상을 HyDE의 정교한 시맨틱 지향적 쿼리 확장이 보완해 줬습니다. 그 결과 **Precision 또한 0.736으로 반등**하며, 복잡한 표(Table) 위주의 문서 환경에서도 쿼리 확장이 최상의 검색 전략임을 증명해냈습니다.

## 5. 핵심 아키텍처 요소: Table Weight & Custom Length Function

마크다운 표본이 통째로 복원될 시 LLM 프롬프트가 지원하는 '최대 토큰 길이를 초과'하는 에러를 막기 위해 **커스텀 가중치 로직**을 새롭게 고안하여 적용했습니다 (`chunking.py`).

1. **가중치 부여**: 마크다운 형식의 테이블은 `|`나 `-` 기호 등으로 인해 일반 텍스트보다 토큰 소비량이 많습니다. 따라서 복원 시 할당할 길이에 **테이블 가중치(예: 1.6x)**를 곱셈 처리합니다.
2. **선행 청킹 (Early Cut)**: 청크 분할기가 문서를 자르기 직전에, 문자 내부의 `[TABLE_x_y]` 영역을 감지하고 가중치가 더해진 어마어마한 테이블 넓이를 미리 예측하여 텍스트를 예상보다 '일찍(안전하게)' 잘라버립니다.
3. 이 기술 도입으로 LLM Context 윈도우 한계를 넘어서는 에러를 원천적으로 차단했으며, 구조적인 안정성에 크게 기여했습니다.

## 6. 결론 및 실무 제언 (Next Step)

1. **테이블 데이터의 1원칙 "분리, 보존, 그리고 병합"**: 금융업 또는 공공기관 기술 보고서처럼 정형 데이터(표)와 비정형 데이터(텍스트)가 엮어있는 문서는 일반 추출기가 한 번에 삼키게 둬선 안 됩니다. PDF 파싱 단계에서 미리 표를 모두 독립 추출(Extraction) 한 뒤 마크다운의 형태로 텍스트 사이에 다시 끼워주는 것이 품질 향상의 황금열쇠입니다.
2. **청크 사이즈의 재조정**: 마크다운 테이블이 포함되는 데이터베이스에서는 행이 잘려나가지 않도록 청크 사이즈를 최소 **512 토큰 이상** 넉넉하게 가져가시길 권장합니다.
3. **HyDE 기반 Hybrid 검색 파이프라인 정립**: 정보의 누락이 치명적인 도메인에서는 Hybrid 방식이 정답입니다. 또한, 질의 의도를 모델이 미리 추론케 하는 **HyDE 기법**을 덧씌우면 키워드(BM25)로 딸려오는 노이즈를 훌륭하게 상쇄하고 Precision과 Recall을 모두 우상향 시킬 수 있는 최적의 검색망이 완성됩니다.
